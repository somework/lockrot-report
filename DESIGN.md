# lockrot-report — design

The renderer behind `lockrot --format=html`, moved out of lockrot's `resources/report/` into its own
repository so it can be worked on as a product and written as a program: TypeScript, components,
tests that open a browser.

This document is the contract the code is written against. The parity inventory it was derived
from (every behaviour of the hand-written page, with file:line citations) lives outside the
repository, in the working notes of the extraction; what matters from it is restated here.

## 1. What ships

`npm run build` writes `dist/`:

| file                 | for                                                        | notes                                                                                                                                                                                           |
| -------------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `report.html`        | lockrot's `--format=html`, lockrot.dev's published reports | Self-contained: CSS and JS inlined. Three placeholders, `{{TITLE}}`, `{{DESCRIPTION}}`, `{{DATA}}`. A `<meta http-equiv="Content-Security-Policy">` pins the inline script and style by sha256. |
| `lockrot-report.js`  | embedders (the viewer's sandboxed frame)                   | IIFE, global `LockrotReport`. Same code as inside `report.html`.                                                                                                                                |
| `lockrot-report.css` | embedders                                                  | Same stylesheet as inside `report.html`.                                                                                                                                                        |
| `manifest.json`      | whoever vendors a release                                  | `{name, version, schema: {report: [2]}, files: {<name>: sha256}, csp: {script, style}}`.                                                                                                        |

Nothing is minified. What lockrot vendors ends up inside a signed PHAR, and a reviewer should be
able to read it; the size cost is small next to the payload.

### 1.1 The template keeps every coupling a consumer relies on

These are depended on by lockrot, by lockrot.dev's scripts and by users' own scripts (`docs/ci.md`
documents a `sed` recipe). They are part of the renderer's public interface:

- exactly one `<script id="lockrot-data" type="application/json">{{DATA}}</script>`, attributes in
  that order, on one line;
- exactly one `<title>` and one `<meta name="description" content="…">`;
- the opening body tag is the literal `<body>`;
- no network reference of any kind: no `fetch(`, `XMLHttpRequest`, `@import`, `import(`, no external
  font, script, stylesheet or image. Links (`<a href>`) are fine; they are navigations, not loads.

The payload escaping is the producer's job and does not change: `</` → `<\/`, `<!--` → `<\u0021--`.

### 1.2 Booting

`lockrot-report.js` does two things when it is evaluated:

1. defines `window.LockrotReport = { version, mount(target, bundle), parse(text) }`;
2. **autoboot**: if `#lockrot-data` exists and holds non-whitespace text, it parses it and mounts
   into `#lockrot-app`.

`mount` returns `{ update(bundle), unmount() }`. Autoboot keeps the old embedding contract working
(write the payload into the slot, then load the script); `mount` is what an embedder should use.

A payload that is not JSON, or not a lockrot document, renders an explained error in place of the
report — never a blank page.

### 1.3 Content-Security-Policy

`report.html` carries, before any script or style:

```
default-src 'none'; script-src 'sha256-…'; style-src 'sha256-…'; img-src data:; base-uri 'none'; form-action 'none'
```

`connect-src` falls back to `'none'`: the page cannot send what it renders anywhere, even if a
future bug lets a document inject markup. Inline `style="…"` attributes in markup would violate the
policy, so the renderer never emits them: dynamic values are set through the CSSOM (Preact's `style`
object prop), which CSP does not govern, or through classes. The e2e suite fails on any
`securitypolicyviolation` event.

An embedder that injects its own markup into a copy of `report.html` (lockrot.dev's provenance band)
must either keep that markup free of inline style/script or replace the meta policy with its own;
`manifest.json` carries the hashes for that.

## 2. Compatibility

- The renderer reads **report schema major 2 only** (`READS_SCHEMAS` in `src/schema.ts`). It
  reads `report.lockrot.schema`, and a document that predates the field reads as 1. A schema-1
  document renders the report-1 screen in place of the report (PD-SCHEMA-1, SPEC §7.9.17): the
  page draws nothing from it and derives no score for it. A higher major renders with a banner
  saying the document is newer than the renderer.
- report-2 is typed by lockrot's TypeScript contract, as lockrot writes it: every key required.
  `normalize.ts` keeps the document as `Model.report`, with its `details`, and every surface reads
  that model alone.
  A document without a root key report-2 requires (`REPORT2_KEYS`) is a `malformed-report` error
  that names the keys. The html embed's `details` has no report-2 type. The model types it from
  explain-2's `lock` and `repositoryMetadata`, plus `repository_link`, which no schema defines.
  Each discriminated union of the contract has one type guard (`isScoreGraded`, `isTermSecurity`,
  `isSecurityVulnerable`, `isSignal`). §7 says where the contract comes from.
  The root-key check proves the root only. Below it the page trusts the shape lockrot wrote, and
  the page ships no validator. A shape that breaks a surface while it renders shows the error
  screen (`ui/RenderGuard.tsx`), never a blank or half-drawn page.
- Unknown fields are ignored. An id the page does not know (a verdict, a flag, a signal, a
  severity, a `next_step.kind`) is kept and printed as written or rendered neutrally, never
  dropped and never a crash.
- Each surface slot (the Findings list, the detail sheet, the overview band, the Run tab, All
  packages, Advisories, Blast radius, the glossary and the printed report) renders its report-2
  component. The shell stays one: `App`, the keyboard, the address, the rail, search, print, theme
  and tabs.
- Fixtures: the pages and unit tests read lockrot's recorded report-2 cases at the pinned commit
  (§6, §7). `fixtures/bundles/mini.json` is the one report-1 input, kept for the test of the
  report-1 screen.

## 4. State and the address bar

State is one object owned by a reducer in `App`:

```ts
{ view, q, pkg, sort, sortDesc, filters: { prio, verdict, scope, signal, sev, fix, since, gate, flag, accepted }, disclosure, example, section }
```

`disclosure` holds the Blast radius rows and folds the reader opened or closed; like `sort` it is not
written to the fragment (PD-RADIUS-3). `example` is the package open when the reader last changed
tab, the score example of "How the score works" (PD-RUN-10); it is not written to the fragment.

The fragment format is a documented user feature (`docs/ci.md`) and **does not change**:
`view=<v>&q=<enc>&prio=<enc a,b>&verdict=…&scope=…&signal=…&sev=…&fix=…&since=…&pkg=<enc>`,
groups in that order, `pkg` omitted while no package is open (the legacy page also left out the
package it opened by itself; this page opens none, PD-ROWS-9), empty state → no fragment.

`view` takes one more value, `overview`, the default view (PD-OVERVIEW-1). Rule R1 decides the view,
so no 0.13 or rc.1 link changes its meaning:

- An empty fragment opens Overview.
- A fragment with no `view` and any other key (`q`, `pkg` or a filter group) opens Findings, as it
  did on rc.1 and 0.13.
- An unknown `view` opens Overview when the fragment has no other key, else Findings.
- The page writes `view` for every view but Overview, so Findings writes `view=findings`. Overview
  writes `view=overview` only beside another key, so that fragment reads back as Overview.

`section=<id>` follows `pkg` under `view=run` only: it opens Run data at that section and moves focus
to its heading (SPEC §7.9.16, PD-PHP-1). A tab switch drops it. On another view, or when the run has
no such section, the key does nothing.

An Overview chart mark is a link to such a fragment (PD-OVERVIEW-7). Always `history.replaceState`, never `pushState`; a `SecurityError` (an
opaque-origin frame) switches writing off for the page's life.

`sev` and `fix` rows come from `score_model.severities[]` and `fix_kinds[]` in `ease` order, under
the fix labels (SPEC §7.9.7). Three groups follow `gate`: `verdict`, the rail's Grade group in `run.graded_verdicts` order (PD-RAIL-7), `flag` (the counted flags, any of) and `accepted`, a view toggle whose
one key `hide` hides the accepted pills and filters no package, so it is no active-filter chip
(PD-RAIL-5). `scope=unnamed` is the "not in composer.json" chip. A 0.13 link opens on report-2
terms: `prio=` as `verdict=`, and a flag in `verdict=` as `flag=`, so `prio` never holds a key
after boot (SPEC §7.9.7).

Changes from the legacy page, each a fix:

- a malformed escape in the fragment skips that piece instead of blanking the page;
- an unknown `view` falls back by rule R1, to Overview or to Findings;
- `hashchange` is honoured (a link pasted into an open page applies);
- a whitespace-only query is not an active filter and is not written;
- the fallback URL keeps `location.search`.

Free text means every word somewhere in the name or the version, beside the field keys `flag:`,
`lead:`, `verdict:` (`priority:` reads as `verdict:`), `score:`, `direct:` and `dev:`, and `q=` is
written as before (SPEC §7.9.7).

## 5. Behaviour: parity, and the deliberate differences

`Enter`, the theme key `lockrot-theme`, boot-only ledger and glossary, "detail stays open while
filters hide it". The legacy auto-open of the first flagged package on wide screens is gone
(PD-ROWS-9).

## 6. Testing

- **Unit** (vitest): every `domain/` and `state/` module, `model/normalize` over every recorded
  report-2 document. The legacy `lib.test.js` cases are ported verbatim as the first tests of
  `format` and `links`.
- **Components** (vitest + happy-dom + @testing-library/preact): the shell and each surface slot —
  the Findings rows, the detail sheet, the overview band, the Run tab, the glossary and the print.
- **E2E** (Playwright, Chromium; Firefox and WebKit in CI): one behavioural suite, run against
  `build/pages/`. It was written and made green against the legacy page first, during the
  extraction, which proved the tests tested something, and ran against both pages until lockrot
  0.12.0 stopped shipping the legacy one; the new page is the only page it runs against since. §5's
  table stays the record of the differences that comparison found and fixed on purpose. Every row
  an e2e test covers carries the row's id in a comment on that test, and later deliberate changes to
  the new page are recorded there the same way; M19 and M24 are covered by a unit test
  instead (its `describe`/`it` name carries the id); M25 is e2e-covered too
  (`e2e/radius-ledger.spec.ts`), alongside its own unit test (`tests/unit/domain/radius.test.ts`).
  M1, M26 and C2 described report-1 surfaces and left with them; M8/M9 and WIDE have no test
  naming their id at all yet. Page-quality checks that apply regardless of any legacy comparison: axe (no
  serious or critical violations), zero CSP violations, both colour schemes, 320/768/1024/1440.
- **report-2 pages**: lockrot records no html embed per case, so `scripts/report2-embed.ts`
  assembles one from the fetched bundle (`npm run contract:fetch`, DESIGN.md §7). `report` is
  `contract/report-2/<case>.json`. `details` holds the case's package from
  `contract/explain-2/<case>.json` as `{lock, metadata, repository_link: null}`, because explain-2
  has no repository link. A case without an explain-2 document (`composite`) has no `details`. Every document of `contract/report-2/` gets a page, because the detail and axe specs open single cases. The two baselined
  embeds (`baselined/*/check/report.bundle.json`) get a page each, used as recorded. The corpus
  slice (`isCorpusSlice`) is `composite`, the offline cases and the two baselined embeds.
  `scripts/pages.mjs` writes them as `report2-<case>.html` and `report2-baselined-<scenario>.html`,
  and plants three pages under `planted/`, which the page sweeps do not list: a report-2 document
  without a root key, the composite with a package named in CSS-selector metacharacters, and
  `fixtures/bundles/mini.json` for the report-1 screen.
  `e2e/support/pages.ts` opens them with `report2Url(<case>)`, and `tests/unit/` imports the same
  module. `e2e/report2-pages.spec.ts` checks that each loads without a console error or an uncaught
  exception.
- **Goldens** (`goldens/en/`): one file per string class, an object keyed by recorded case, written by

  like a snapshot. A class that lockrot's PHP grammar owns (the Age row, the baseline suffix) is

- **Build checks**: the built `report.html` contains each coupling in §1.1 exactly once, none of the

## 7. Release and vendoring

- A tag `vX.Y.Z` builds `dist/`, attests it (`actions/attest-build-provenance`) and attaches the four
  files to a GitHub release.
- The release runs in three jobs. The gates job installs, tests and builds, and records the
  sha256 of its four files. The build job installs with `--ignore-scripts` and builds the files
  that ship. Both run with a read-only token and keep no checkout credentials. The publish job runs
  none of the repository's code. It checks the shipped files against the gates job's digests, then
  attests them and creates the release. Only it holds `id-token` and write permission. Code that a
  build itself runs can still change the files in both jobs alike, so the check stops an install
  script or a test, not a compromised build tool.
- A tag with a pre-release suffix (`vX.Y.Z-rc.N`) takes the same path and publishes a pre-release
  that never becomes the Latest release. Its notes are the `## [X.Y.Z-rc.N]` CHANGELOG section, else
  the `## [X.Y.Z]` one; with neither, the release fails. `package.json` carries the rc version, so
  the guard `v` + `version` = tag holds unchanged.
- `manifest.json` holds `name`, `version`, `schema.report` (the list `READS_SCHEMAS` in
  `src/schema.ts`, which `NewerSchemaBanner` also reads), `files`, `csp` and `contract`.
  `contract` is `{bundle_sha256, score_text_grammar, text_grammar}`, copied from `contract/lockrot.json`,
  the pin of the lockrot bundle this renderer was tested against. lockrot's `RendererManifestTest`
  compares the three values with its own.
- lockrot vendors `report.html` and `manifest.json` into `resources/report/`; its `HtmlFormatter`
  fills three placeholders. An update script downloads a release, verifies the attestation with
  `gh attestation verify`, checks sha256 against the manifest and writes the files; lockrot's CI
  checks the vendored bytes against the manifest.
- lockrot.dev takes `lockrot-report.js`/`.css` for its frame and `report.html` for published
  reports from a renderer release instead of from a lockrot tag.
- The renderer reads lockrot's rendering contract at one lockrot commit, pinned in
  `contract/lockrot.json` with the `bundle_sha256` of lockrot's recorded bundle and the two
  grammar versions (`text_grammar`, `score_text_grammar`). `contract/` also commits the files the
  build needs at that commit: the report-2 and explain-2 schemas and the d.ts pair. The build reads
  only committed files.
- The recorded bundle is not committed. `npm run contract:fetch` (`scripts/contract.mjs`) makes
  `.lockrot/` a shallow, sparse checkout of lockrot at the pinned commit, so every file keeps
  lockrot's relative path. It holds every file `bundle_sha256` covers, `bundle.generated.ts`,
  `flags/cases.json` and `types/`. The script recomputes the hash as lockrot's
  `ContractBundle::sha256()` does. It fails when the hash, a grammar version or a committed
  `contract/` file differs from lockrot's. An unchanged checkout at the pinned commit needs no
  network. A changed, missing or extra file makes the script fetch again, because the hash does not
  cover `bundle.generated.ts` and `flags/cases.json`. The script also fails when either is missing.
  CI caches `.lockrot/` by the pinned commit and the fetch script.
- What checks the contract: `types-match-schema.test.ts` validates every recorded report-2
  document, both baselined html embeds and their `details` with ajv (draft-04), and runs each type
  guard on every document. `npm run typecheck:contract` compiles `bundle.generated.ts`
  (`<document> satisfies Report2`) and the d.ts pair with `skipLibCheck` off.
- A contract change in lockrot moves the pin: `npm run contract:repin <lockrot commit>` checks out
  that commit, checks its files against its own `bundle_sha256`, and rewrites
  `contract/lockrot.json` and the `contract/` files. The diff of `contract/` is the review.
- Order of changes across repositories: data first in lockrot (schema minor, renderer ignores
  unknown fields), rendering second here, the pin bump in lockrot's release PR.

## 8. Layout and interaction

The shell (`src/ui/App.tsx` and its neighbours) keeps the legacy page's visual language (tokens,
type, tones, vocabulary) and changes layout only where the legacy page failed a reader.

**Breakpoints.** Three, all driven by `matchMedia` in `ui/useWide.ts` and mirrored in
`ui/app.css`:

| width        | layout                                                                                                                |
| ------------ | --------------------------------------------------------------------------------------------------------------------- |
| ≥ 1181px     | rail · list, plus a detail column once a package is open (the legacy WIDE layout)                                     |
| 760 – 1180px | rail · list; the detail opens as a full-screen sheet                                                                  |
| < 760px      | one column: on Findings the PD-SUMMARY-16 strip, a "Filters" disclosure, then the list; Overview in its reading order |

The legacy page pushed the findings below the whole ledger and the whole rail at 320px, so a phone
reader scrolled past two screens of bars and buttons before the first package. The summary band
lives on Overview, the default view, unfolded (PD-OVERVIEW-2). Findings opens with one line: the
flagged figure and the grade chips (PD-SUMMARY-16). Under 760px the rail becomes a
closed `<details>` whose summary counts the rail filters that are on. The Findings rows follow the
list's own width, not the viewport's (a container query, PD-ROWS-4): one line from 990px of list,
three below that, the list beside an open package (570-790px at 1280-1920) included (PD-ROWS-14).
With nothing
open, which is how every page without `#pkg=` loads (PD-ROWS-9), the list is 910-1230px at
1181-1920, so a wide screen's first sight is one line a row from 1440px up. At every width a cell
too narrow for its value wraps it, never an ellipsis.
Opening a package there switches the list to three lines a row, and closing it back, so every row
above the one acted on changes height. `ui/rowAnchor.ts` measures that row before a `select` is
dispatched (a click, Enter, `j`/`k`, Close, Escape) and `App` scrolls the page by however far it
moved before the browser paints, so it stays where the reader saw it (PD-ROWS-10). Near the end of
a short page that scroll would pass the page's end, so `App` adds the missing height below the list
(`--anchor-room`) until the next state change. `html`'s
`scroll-padding-top` keeps a row brought into view clear of the sticky header and column head.

**The summary band's lead** is Overview's first five seconds: how many packages are flagged, out of how
many were checked, with the grade chips that filter by it and a waffle of every package
(PD-SUMMARY-6, PD-SUMMARY-11), then `gate.text` as lockrot wrote it (PD-GATE-6). The header keeps
the short gate fact (below).

**Sticky offsets are measured, not guessed.** Only the header band (brand, run facts, tabs) is
sticky, and only from 760px up. `Header` publishes its real height as `--topbar-h` through the
CSSOM (a ResizeObserver); the rail and the detail column stick under it and scroll on their own
when taller than the viewport. The legacy page hard-coded 196px and overlapped a wrapped header. The
Findings list's column head (PD-ROWS-4) sticks under it too, within the list, so the age axis'
captions stay over the bars they measure.
Both columns are at most `--sticky-room` tall (`ui/app.css`): the viewport less the topbar and a
16px gap on each side. At the page's end the footer takes the bottom of the viewport, so while the
footer is on screen `--sticky-room` also subtracts `--footer-h`, never below 50vh; `Footer.tsx`
measures it and toggles `:root.footer-in-view` from an IntersectionObserver. Subtracting it only
while the footer is visible keeps a usable column on a short viewport. The columns' row is never
shorter than the full `--sticky-room`, so a column that gives up the footer's height never shortens
the page: on a short list the rail set the page's height, and reaching the footer shortened the page
by the footer's height and slid every row down by as much (PD-ROWS-10). Where the 50vh floor wins,
the panel's top slides under the header at the page's end, an accepted limitation (PD-DETAIL-5).

`.shell-detail` (`is-side`/`is-sheet`) alone owns the detail's geometry and scrolling; `Detail`
only lays out its children, and opening another package starts at the top (PD-DETAIL-3). A wheel
over `is-side` chains into the page once its own content ends, since page scroll is what carries it
from its in-flow position into its stuck one (PD-DETAIL-5). `is-sheet` keeps
`overscroll-behavior: contain`: it covers a page whose scroll is locked (M13).

**The detail panel** follows SPEC §7.9.8.2's order: the header (name, version, grade chip, flag
pills, out-links; the only part that sticks), the verdict block, the move card with its Held by and
each Then card with its own (PD-DETAIL-16, PD-DETAIL-15), "Why {verdict}" (PD-DETAIL-13), then one
row each for Checks, Security and Advisory feeds, the Release branches section across the sheet
with its timeline (PD-TIMELINE-18), then one row each for Age, Repository and the baseline.
"The lock entry" and "Provenance" come last, each a `<details>` closed by default
(PD-DETAIL-1/PD-DETAIL-2).

**Tabs** follow the ARIA tabs pattern: one tab in the Tab order, arrows/Home/End move and select,
the current view's column is the `tabpanel`. When the tab row overflows it scrolls sideways
(PD-TABS-1): each side with tabs out of sight fades into the header's surface under a chevron
button that pages the row, and the selected tab is scrolled into full view on load and on every
switch, instantly under reduced motion. The chevrons sit outside the `tablist`, `tabIndex=-1` and
`aria-hidden`: pointer affordances only, since the single Tab stop and the arrow keys already reach
every tab. In forced colours the fade goes and the chevrons keep the system's button colours.

**The detail sheet** locks page scroll only while it is shown with content in it (M13). The
glossary is a native `<dialog>`; where `showModal()` throws it opens non-modal but pinned
`position: fixed` over the page with a spread-shadow backdrop, and focus is moved in and returned
by hand (M28). It opens with the verdicts and the flags in view, the other sections folded
(PD-GLOSSARY-2).

**Folds.** Every `<summary>` on the page draws one marker, a CSS-drawn triangle in
`styles/base.css`, not a text glyph whose shape depends on the viewer's fonts; a surface styles only
its summary's layout (PD-DISCLOSURE-1).

**Forced colours** flatten authored colours to the page background, so every mark drawn from a
background or border (ledger bars, legend chips, the score bar and its ruler, the age scale, the
fold marker) has its own `@media (forced-colors: active)` rule in system colours, and a score
segment shows its role by its border's style (PD-SCORE-3). `e2e/forced-colors.spec.ts` emulates the mode.

**Keyboard** decisions are one pure function, `ui/keyboard.ts#decideKey`:

- `j`/`k` move from the row that holds focus, else the open package, through the rows the current
  view draws (`views/order.ts#renderedPackages`), clamped at both ends; with neither on screen,
  both start at the first row. There is no separate cursor, so a row clicked, a package opened from
  an advisory, or the row Escape just handed focus back to is where `j` continues from (fixes M7–M9;
  the legacy first `j` after its boot pick re-selected the same package). On load nothing is open,
  so `j` opens the first row. Focus moves to the row `j`/`k` open, as it stays on a row clicked
  (PD-ROWS-10), so focus and the open package agree and Enter opens the row on screen as open
  (PD-ROWS-11). The row is brought into view with `block: "nearest"`, `behavior: "smooth"` unless
  `prefers-reduced-motion: reduce` (checked in script: a CSS `scroll-behavior` would also glide
  PD-ROWS-10's instant `scrollBy`). A row is placed by its position among the view's rows, not its
  name, so a package listed twice is walked row by row (PD-ROWS-12).
- A sheet (below 1181px) covers the whole page, so a row under it can hold no visible focus
  (WCAG 2.4.11). A reader's own open (click, Enter, `j`/`k`) puts focus on the sheet's heading
  (`[data-detail-focus]`, `tabindex="-1"`), and the header, summary, rail, list and footer are
  `inert` while it is up: Tab stays in the sheet. `j`/`k` still walk the list under it, re-focusing
  the heading so it is announced; Escape and Close hand focus to the row reached; `/` closes the
  sheet on its way to the search box. A `#pkg=` sheet on load leaves focus alone (PD-ROWS-12).
- Roving tabindex (`ui/rowCursor.ts`, PD-ROWS-11): one row of the list has `tabindex="0"` — the open
  package's, else the one last opened, else the first — every other row `-1`, and the links inside
  a row are `-1` except on that row. Tab reaches the list once, then that row's links, then the
  detail. A package listed twice (Advisories, Blast radius) is a Tab stop on its first row only;
  every one of its rows carries `aria-current` while it is open (PD-ROWS-12).
- Nothing but Escape acts while the glossary is open (M10). Printable shortcuts are ignored while
  focus is in any text field, and every shortcut is ignored with Ctrl, Meta or Alt held.
- Enter/Space toggle a row only when the key lands on the row itself, not on a link or control
  inside it (M5).
- The undecided gate fact (PD-SUMMARY-2) is a native `popover="auto"` element opened by a
  `<button popovertarget>`. It never traps focus, so `j`/`k`/`?` still act while it is open. Escape is left to the browser, which closes an open
  popover on its own (`decideEscape` returns `ignore`).
- Escape closes one thing per press: an open popover first (PD-GLOSSARY-6/PD-SUMMARY-4), then the
  glossary, then detail (focus returns to the row whose `data-pkg` equals the closed package, found
  by attribute comparison; pressed in a text field, focus stays in the field, PD-ROWS-11), then the
  search box, handing focus to the list's Tab stop (none on a tab without rows: it just blurs,
  PD-ROWS-12).
- Overview draws no row and no search box, so `/`, `j` and `k` do nothing there and leave the key
  to the browser. No key moves the reader to another tab. The glossary's "Keys and search" names
  `/`, `j`, `k` and Enter as keys of a tab with a list, and Esc and `?` as keys of every tab. Tab
  goes from the header to the tab row, then through the Overview links in reading order.
- Overview and the Findings strip sit inside `<main>` with the shell, so no content is outside a
  landmark.

**Theme.** The button names the action relative to the _effective_ theme, the pinned one or the
OS preference (M11). The choice persists under `lockrot-theme`; an unrecognised stored value is
ignored rather than written onto the page.

**The gate fact** is a quiet fact in the header, beside "lockrot `<version>`". With lockrot's root
`gate` decided, it is words only: "this run fails · `--fail-on=high`", "baseline run passes ·
`--fail-on` not applied" (PD-GATE-1). A run that passed with `--fail-on=none` shows "no gate", or
"gate: strict network", opening a popover with what the run was told (PD-SUMMARY-2). The lead
prints `gate.text` in full (PD-GATE-6).

**Address bar.** `ui/useHashState.ts` reads the fragment once at boot and nothing else: a `pkg=` in
it opens that package at any width and scrolls its row into view, and without one no package is
open (PD-ROWS-9, PD-ROWS-10). It writes after every state change, and applies `hashchange` by
replacing the state from the new fragment while keeping the table's sort order.
